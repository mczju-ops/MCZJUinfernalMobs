## 记录规则

- **已确认**：从当前代码可以直接确认的行为或结构问题。
- **待确认**：代码存在风险或语义不清，但需要结合服务器实际表现、配置和预期玩法再决定。
- **优先级**：按数据安全、玩家可见影响、长期运行风险和维护成本粗略排序，不代表实施顺序已经确定。
- 完成处理后不要直接删除条目，应补充处理方式、日期和相关提交。

## 已确定的重构约束

### 配置与数据迁移策略

- 重构开发期间不要求新版代码兼容旧版配置结构。
- 重构完成后关闭服务器，在停服状态下手工将正式服配置和数据迁移到新版目录与 schema，再启动服务器。
- 新版源码只读取新版格式，不保留旧键别名、双格式探测、自动迁移器或其他旧版兼容分支。
- 手工迁移前应备份完整的 `plugins/InfernalMobs/` 目录，并使用新版加载器对迁移结果进行完整校验。
- 即使不兼容旧格式，仍建议在新版根配置中加入 `config-version`，用于识别未来版本和明确拒绝不受支持的格式，而不是静默套用默认值。

### `/im reload` 语义

- 重载采用“完整解析、完整校验、一次提交”；任意必需配置文件解析失败时，本次重载整体失败并继续使用旧快照。
- 区域、等级范围、词条池和预设只影响重载后新生成的炒鸡怪。
- 已存在的炒鸡怪保留生成时确定的等级与词条组合。
- 技能概率、冷却、伤害和其他运行期参数在下一次触发时读取新配置快照。
- 已经应用的装配型 `STAT` 效果不追溯重装：不重新发放装备、不重新生成坐骑，也不重新计算现有怪物当前血量。
- 插件级调度任务（例如怪物注册表清理）根据新配置安全重建或更新。
- 掉落与保底规则在提交后立即使用新配置，但玩家已有保底进度必须保留，相关服务实例不得因重载被替换。

### 炒鸡怪实体状态与原版自然消失

- 炒鸡怪继续遵循原版生物自然消失规则；插件不得通过设置持久实体等方式阻止距离消失。
- “持久化炒鸡怪状态”是指补全实体自身的 PDC 数据，由世界区块存档随实体保存，不额外建立怪物 YAML 数据文件。
- PDC 至少需要保存数据版本、等级、词条 ID、禁用词条、已消费的一次性机会和区域变形目标池。
- 区块卸载时结束该实体的内存会话并注销 `MobState`；实体若未按原版规则消失，重新加载后根据 PDC 恢复 `MobState`。
- 服务器启动时恢复当前已加载区块中的炒鸡怪，后续通过实体加载事件恢复其他区块。
- 恢复时不重新执行 `onEquip`，避免重复装备、生成坐骑或重新计算生命值。
- 冷却、临时 Buff、正在执行的技能会话和延迟任务不写入 PDC，重新加载后重置。
- 词条禁用、一次性机会消费和变形等持久状态发生变化时，必须同步更新实体 PDC。
- 废除“发现实体带有 `im_level` 但未注册就直接删除”的机制，并移除对应的 `/im cleantags` 指令及定期清理调用。

### 名称与本地化

- 原版实体名称使用 Adventure 翻译组件，由玩家客户端语言决定，不再维护实体中文名映射。
- 原版物品和 ItemCreator 物品使用实际 `ItemStack` 的有效名称组件，保留物品自定义名称与样式。
- 删除 `mob_name.yml` 和 `loot_name.yml`。
- 自定义词条没有可复用的原版翻译键，词条名称统一放入 `skills.yml`，删除重复的 `skill_name.yml`。
- 消息模板继续使用 MiniMessage，但实体名、物品名等以 `Component` 占位符插入，不先转换成普通字符串。

### 对外 API 调整范围

- 本轮重构允许根据新模型调整 MCZJUInfernalMobs API，不要求无条件保持现有签名。
- API 变化必须有明确收益，例如正确传递 `Component`、暴露稳定只读快照或消除旧配置模型泄漏；不进行无关的破坏性改名。
- 发生不兼容变化时，同步修改独立 API 项目、提升 `apiVersion`，并更新 `docs/api.md` 和对接示例。

### 配置项暴露范围

- 第一轮保留所有确实影响玩法和平衡的参数，包括概率、冷却、伤害、持续时间、范围、数量、实体池、物品 ID 和技能几何参数。
- 删除可以从代码确定的重复字段，例如 `skills.<id>.type`，以及可推导数据和重复名称映射。
- `skills.yml` 完整列出所有允许调整的参数；文件可以较长，但只承担技能领域配置。
- Java 中仍提供安全默认值用于局部缺项降级，随插件发布的默认配置则保持完整，不依赖大量隐藏默认值。
- 不因某个参数当前较少修改就直接将其硬编码；完成配置快照和类型校验后，再依据实际维护经验进行第二轮删减。

### 配置错误与降级策略

- 配置错误不得导致整个插件被禁用；插件保持启用并进入可诊断的降级状态。
- `/im reload` 采用全量提交：任意必需配置文件无法形成有效新快照时，本次重载整体失败并继续使用旧快照。
- 首次启动没有旧快照时，按配置领域使用源码中的保守安全默认值；未知 `config-version` 不做兼容解析，同样进入安全降级状态。
- 已存在插件目录时，缺失或损坏的配置文件不自动覆盖，避免破坏管理员现场；日志必须说明文件、路径、原因和实际回退行为。
- 单项类型错误或越界时使用安全默认值；无法成立的单个区域、预设、掉落或保底规则只跳过对应条目。
- 未知配置键产生警告，用于发现拼写错误；错误与警告集中在加载阶段输出，不进入战斗高频日志。
- 核心和技能配置使用内置默认参数；区域错误时回退空区域及全局规则；消息错误时使用内置中文消息。
- 掉落配置无法可靠加载时关闭插件掉落并保留原版掉落，禁止回退到可能启用 `replace-vanilla-drops` 的普通默认配置。
- 保底配置无法可靠加载时暂停累计和发放，但不得清空已有进度。
- 插件需要保留当前配置状态（正常或降级）及诊断信息，并在启动日志和 `/im reload` 结果中明确报告。
- 配置错误与运行数据损坏分开处理；玩家数据不得通过普通配置默认值机制清空或覆盖。

### 运行数据保存策略

- 不引入数据库、备份轮换、只读保护状态或专门的数据损坏恢复机制，保持当前服务器规模下的简单文件模型。
- 插件启用时将击杀统计和保底进度从 YAML 加载到内存；运行期查询和修改只针对内存状态。
- 运行数据统一放入 `data/`，按固定周期异步落盘；插件正常关闭时额外执行一次最终落盘。
- 异步保存前生成稳定的内存快照，后台任务只序列化并写入该快照，不直接遍历仍在变化的运行时集合。
- 同一数据文件的保存任务不得重叠；保存期间产生的新修改必须在后续周期继续保持为脏状态。
- 只有保存成功后才清除对应脏状态；保存失败记录中文错误并在下个周期重试。
- `/im reload` 只更换配置快照，不重建数据服务、不重新读取或清空玩家数据。
- 数据文件无法加载时记录明确错误并按现有简洁模型处理，不为此增加特殊运行状态；数据备份和异常恢复由停服运维负责。

### 新版目录布局

```text
plugins/InfernalMobs/
├─ config.yml
├─ skills.yml
├─ regions.yml
├─ messages.yml
├─ loot/
│  ├─ settings.yml
│  ├─ guaranteed.yml
│  └─ levels/
│     ├─ 1.yml
│     ├─ 2.yml
│     └─ ...
└─ data/
   ├─ kill_stats.yml
   └─ guaranteed_loot_progress.yml
```

- `config.yml` 保存全局行为，并作为整套配置唯一的 `config-version` 入口。
- `skills.yml` 保存全局词条权重、词条显示名和全部允许调整的技能参数。
- `regions.yml` 保存基础生成规则、空间区域及其有限覆写；新版移除未使用的预设怪物。
- `messages.yml` 保存死亡播报、保护动物警告及其他可编辑文本模板。
- `loot/settings.yml` 保存掉落总开关、原版掉落替换、抽取次数、轮换，以及原 `special_loot.yml` 的特殊实体额外掉落配置；特殊掉落功能保留为 `special` 配置段。
- `loot/guaranteed.yml` 保存保底规则，`loot/levels/` 保存逐等级奖励池。
- `data/` 只保存插件运行数据，与管理员配置明确分离。
- 删除 `mob_name.yml`、`loot_name.yml`、`skill_name.yml` 和示例文件 `loot/eg.yml`。

### 区域与生成规则模型

- 采用“标准规则 + 特殊区域有限覆写”模型，不在配置表面引入多层 profile 继承。
- 配置中提供一套标准生成规则，特殊区域只覆写明确允许的玩法字段；当前重点覆盖等级分布、词条池、词条数量规则和变形目标池。
- `affix-count` 明确属于区域难度规则，必须支持区域覆写。它表示炒鸡怪生成时的词条总数规则；在“几级对应几条词条”的配置下，新手区可通过等级权重限制在最高 5 级，困难区可使用最高 15 级，必要时也可单独调整数量公式、上下限。
- 新版词条数量只保留 `formula: level`：词条数量按生成等级计算，再受 `min`、`max` 边界保护；删除历史遗留的 `tier` 公式和 `tier-threshold` 配置，不保留兼容分支。
- 等级分布终版只使用逐等级权重表，例如 `levels.weights.1`、`levels.weights.2`；删除未使用的 `base`、`scale`、`max`，也不再保留 `level-min/max` 与 `level-ranges` 两套表达。
- `skill-pool` 引用 `skills.yml` 中的命名词条池。特殊区域配置 `skill-pool` 时整体替换标准词条池，不进行逐词条隐式合并；未配置该字段时继承标准规则。
- 其他覆写字段遵循同样的有限字段规则：字段出现即整体替换，字段缺失才继承标准值。不支持任意深层 YAML 合并、池继承或多层 `extends`。
- 第一版不提供区域级 `entity-filter` 覆写。当前服务器实际玩法中不同区域没有实体类型差异，先不为此引入字段和合并语义；现有全局实体类型限制是否保留，需在迁移现有正式配置时单独核对，不能未经确认直接删除。
- 已确认移除全局 `deny-types`。新版不再提供实体类型黑名单；全局 `allow-types` 是否仍需保留，待迁移正式服配置时核对实际用途。
- 已确认移除预设怪物功能。当前正式服没有使用预设配置，新版不保留 `presets` 模型、解析器和相关生成分支。
- 标准规则与区域空间匹配分离。标准区域可以是普通坐标区域；未命中任何区域时使用显式的全局默认规则，不因区域 ID 叫 `standard` 而产生隐式默认语义。
- 区域支持明确的 `priority`。位置命中多个区域时选择优先级最高者，同优先级使用稳定的配置顺序；不得依赖 `HashMap` 遍历顺序。
- 加载配置时将基础规则和区域覆写解析为每个区域的完整不可变最终快照（内部可称为 `ResolvedSpawnRules`）。生成运行期不再临时合并配置。
- 等级与词条选择必须在本插件自己的生成流程中完成。生成事件只广播最终结果；不得依赖外部监听器在事件阶段临时修改等级、词条池或内部状态。
- 该模型的目标是降低配置理解成本，同时保留 reload 的完整快照语义和生成结果的一致性。

### PDC 实体状态方案

- 新版使用插件命名空间 `mczju` 下的独立 `infernal_mob` `TAG_CONTAINER` 作为炒鸡怪标记和状态容器，不再把 `im_level` 作为完整身份判断依据。
- 容器字段固定为：`data-version`（整数）、`level`（整数）、`affixes`（按生成顺序保存的词条 ID 字符串）、`suppressed-affixes`（已禁用词条 ID 字符串）、`used-one-time`（已消费的一次性机会 ID 字符串）和 `morph-targets`（有效变形目标 EntityType 名称字符串）。
- 词条 ID、禁用 ID 和一次性机会 ID 使用小写、逗号分隔的字符串编码；ID 本身禁止逗号。空集合写为空字符串或删除对应字段，读取时按空集合处理。
- `morph-targets` 保存生成时解析出的有效目标池，而不是只保存区域 ID；这样配置 reload 或区域改名不会改变现有实体的变形目标。未配置区域专属池时，也保存当时生效的全局目标池。
- 当前旧实现只有在区域显式配置 `morph-types` 时才会在生成/装配前把目标池放入 `MobState`；未配置区域池时保存 `null`，`DualMorphSkill` 会在触发时重新读取全局技能配置。新版必须消除这一差异：无论来源是基础规则还是区域覆写，都在生成/装配前解析最终目标池，并同步写入 `MobState` 与 PDC。
- PDC 只保存跨区块卸载和服务器重启仍需保留的生成/玩法状态：等级、词条、禁用状态、一次性机会和变形目标池。冷却、临时 Buff、技能会话、延迟任务和 `StatMap` 不持久化，恢复后重新建立运行期状态。
- 新实体在完成 `MobProfile`、区域最终规则和初始词条后一次性写入完整 PDC；禁用词条、一次性机会消费和变形完成后通过统一方法重写完整状态容器，避免散落写入。
- 恢复入口包括服务器启动时已加载实体和实体/区块加载事件。恢复只重建 `MobState` 和必要的名称/技能运行状态，不重新执行会重复装备、生成坐骑或修改初始生命值的 `onEquip` 流程。
- `data-version` 只用于识别当前 PDC schema；不支持的版本、缺失字段或无法解析的内容只记录一次中文警告并保留实体，不删除实体、不执行孤立标签清理。能够解析的字段可按安全规则恢复，无法恢复的实体保持未注册状态，等待原版自然消失或管理员处理。
- 旧版 `im_level` 不再作为新版注册依据，也不触发删除；正式迁移时由停服运维决定如何处理仍带旧标签的存量实体。
- 实现记录（2026-09-28）：已增加 `mczju:infernal_mob` 容器编解码、生成及持久状态变化同步、服务器启动与 `EntitiesLoadEvent` 恢复、`EntitiesUnloadEvent` 注销。恢复不调用完整 `onEquip` 或 `applyStats`；旧 `im_level`、不活跃清理、关服杀怪和 `/im cleantags` 已退出运行代码。

### 变形状态继承

- 变形时继承等级、词条、词条禁用状态和已消费的一次性机会。
- 变形时不继承冷却、临时 Buff、正在执行的技能会话和其他仅属于旧实体运行期的状态；这些状态在新实体上重新开始。
- 新实体重新执行必要的装配效果，但一次性机会不得因变形刷新；`1up`、巨型蛛网等已消费机会必须继续保持已消费状态。
- 该语义符合当前策划：变形是新实体运行会话的开始，但不是重置持久玩法状态。具体注销顺序和 `onUnequip` 调用时机在实现生命周期时统一确定。

### 开发前决策审计

- **已定稿、可以进入实现**：停服手工迁移且不兼容旧配置；完整快照式 reload；标准规则与特殊区域有限覆写；等级逐级权重；`affix-count` 只使用 `formula: level`；命名词条池；PDC 实体状态恢复；原版自然消失；简单内存数据服务与异步落盘；删除自定义孤立实体清理；保底按等级池抽取次数累计。
- **已定稿、实现时验证顺序**：变形继承等级、词条、禁用状态和一次性消费记录；重置冷却、临时 Buff 与技能会话；新实体重新执行必要装配，且不得刷新已消费的一次性机会。具体注销顺序和 `onUnequip` 调用时机仍需在实现生命周期时统一处理。
- **实现时核对、暂不阻塞配置模型**：现有全局实体类型允许/禁止列表是否仍有正式服用途（第一版不提供区域级过滤）；正式服实际 Paper/Java 版本，用于最终统一 `plugin.yml`、构建描述和 API 文档；当前是否有启用中的预设怪物配置。
- **可以边开发边完成**：`ResolvedSpawnRules` 等内部类命名、PDC 具体键名、配置诊断对象结构、技能任务拆分边界、API 破坏性调整的具体签名。
- 因此可以开始配置模型和加载器的基础实现，但在接入变形生命周期、整理全局 `allow-types`、发布最终默认配置和完成正式服迁移前，必须完成上述核对。
- 新版运行环境目标确定为 Java 25，Paper API 使用 `[26.2.build,)` 的 Maven 版本范围；README、`pom.xml`、`plugin.yml` 和 API 文档应统一到该目标。

### 保底进度语义

- 保底进度按玩家击杀时实际获得的“等级池抽取次数”累计，不按怪物数量累计。
- 每次符合基础条件的死亡只计算一次 `drop-times`，同一结果同时用于普通等级池抽取次数和保底进度增量。
- 等级掉落关闭、ItemCreator 不可用，或当前等级经轮换过滤后没有可用奖励时，本次抽取次数为 0，保底不增长。
- 某次抽取选中的物品最终创建失败时，该次机会仍计入进度，不反向扣减。
- 特殊实体额外掉落、保底奖励本身和 API 主动抽取不增加保底进度。
- 同一个进度规则每次死亡只累计一次，不能因存在多个轮换奖励而重复累计。
- 新版配置使用 `required-rolls` 表达触发阈值，不再使用容易被理解为击杀数的 `count`。
- 共享进度改为“一个进度规则包含多个轮换奖励”，不再通过多条规则重复填写 `progress-id` 实现。
- `reset-after-reward: true` 时达标后直接归零，不保留超过阈值的部分；否则标记为已完成并停止累计。
- README、配置注释和 API 文档统一使用“等级池抽取次数”描述该机制。

### 炒鸡怪清理规则

- 删除整个 `mob-registry` 配置段和 `MobRegistryConfig`，不再维护插件自定义的不活跃距离与超时删除规则。
- 删除对应的定期清理任务和 `kill-on-shutdown` 行为，服务器关闭时由世界正常保存仍然存在的实体。
- 炒鸡怪何时自然消失交给原版生物规则；插件只注销已经无效、死亡或自然消失实体的内存状态。
- 保留 `/im clear [半径]` 作为管理员明确发起的实体清理操作。
- PDC 恢复机制只恢复仍然存在的实体，不得设置阻止原版自然消失的持久标记。
- 实施后必须在实际 Paper 服务器仔细验证：删除自定义清理规则后，炒鸡怪是否仍会在玩家远离时按照预期自动消失，并检查区块卸载、重新加载和服务器重启三种场景。

### 2. 重载会替换保底服务，可能丢失尚未落盘的进度

- 状态：**已处理，待测试服验证**
- 现状：`reloadLootConfig()` 每次都会创建新的 `GuaranteedLootService` 并从文件重新加载，但替换旧实例前没有调用旧实例的 `saveIfDirty()`。
- 后果：玩家在上一次定时保存后产生、尚未落盘的保底进度，可能在执行 `/im reload` 时丢失。
- 位置：`InfernalMobsPlugin.java` 的 `reloadLootConfig`、`reloadRuntimeConfig`
- 建议方向：优先考虑让服务实例保持稳定并只替换不可变配置快照；若确需替换实例，必须先可靠保存或迁移内存状态。
- 处理记录：2026-09-28 `GuaranteedLootService` 改为插件生命周期内的稳定实例，启动时只加载一次进度；新版掉落 reload 只更新配置引用，不再替换服务或重读数据文件。

### 3. 持久化失败后不会自动重试同一批脏数据

- 状态：**已实现，待测试服验证**
- 现状：`KillStatsService.saveIfDirty()` 和 `GuaranteedLootService.saveIfDirty()` 都在实际构造并写入 YAML 前将 `dirty` 设为 `false`。
- 后果：如果文件创建或保存失败，且之后没有新的数据变化再次设置 `dirty=true`，后续定时保存不会重试，关服保存也可能跳过。
- 位置：
  - `service/KillStatsService.java` 的 `saveIfDirty`
  - `service/GuaranteedLootService.java` 的 `saveIfDirty`
- 建议方向：只在成功完成保存后清除脏标记；同时评估完整文件替换，避免写入中断留下损坏文件。
- 处理记录：2026-09-28 两个运行数据服务改用版本号和稳定深拷贝快照；写盘成功后才确认对应版本，失败保持待保存状态。定时与关服保存共用互斥边界，不会重叠。

### 6. 主配置重载不是完整快照替换

- 状态：**已处理，待测试服验证**
- 现状：`ConfigLoader.load()` 先调用 `plugin.reloadConfig()`，随后逐字段修改当前 `ConfigLoader` 的成员。
- 风险：解析中途发生异常时可能留下新旧字段混合状态；YAML 根本性加载失败时也没有显式保留上一个可用快照。业务类还可以通过 `getRaw()` 读取原始可变配置。
- 位置：`config/ConfigLoader.java` 的 `load`、`reload`
- 建议方向：解析到临时不可变配置对象，完成校验后一次替换；重载失败时保留旧快照并向管理员返回失败结果。
- 处理记录：2026-09-27 建立 `ConfigSnapshot`、新版四文件解析器和集中诊断；2026-09-28 新增完整预解析的掉落/保底快照，`/im reload` 在全部必需域解析成功后才提交，失败保留旧配置与保底内存进度。

### 7. `mob-registry` 清理参数重载后不会完整生效

- 状态：**保底说明已处理，词条清单待最终整理**
- 现状：`CombatService.startTickTask()` 只在启用阶段读取一次 `MobRegistryConfig` 并创建清理任务。`/im reload` 不会取消、重建或更新该任务。
- 后果：运行中修改 `cleanup-enabled`、间隔、半径或不活跃时间后，实际任务可能继续使用旧值；启动时关闭清理后，运行中启用也不会创建任务。
- 位置：`service/CombatService.java` 的 `startTickTask`、`InfernalMobsPlugin.java` 的 `reloadRuntimeConfig`
- 建议方向：把任务重配作为配置提交的一部分，显式取消并按新快照重建清理任务，同时防止主 tick 任务重复启动。

### 8. 触发管线的职责和概率判定位置不一致

- 状态：**已确认（结构问题）**
- 现状：

  - `PASSIVE`、`ACTIVE`、`DUAL` 的概率通常由各 Skill 自行判定。
  - `1up` 虽为 `STAT`，但由 `CombatService` 单独实现运行期触发，且不经过通用 Attempt 管线。
  - `spear`、投射物、烟花和闪电等又存在额外命中/逐受害者管线。
- 风险：新增或修改词条时容易遗漏 Attempt、Triggered、冷却提交、取消语义或目标校验；仅阅读 `Skill` 接口无法得到完整规则。
- 位置：`service/CombatService.java`、`skill/Skill.java`、各 `skill/impl` 类
- 建议方向：先写清楚各阶段契约，再抽取小型触发协调器或公共模板；不能为了统一外观而破坏现有 API 事件时机和取消语义。

### 9. 长时技能状态分散在全局 Skill 实例中

- 状态：**待确认**
- 现状：`SkillRegistry` 为每个 ID 保存一个全局 Skill 实例。大多数实现无状态，但 `PassiveLifestealSkill`、`RangeSpearSkill` 在实例字段中维护按 UUID 索引的活动任务/会话。
- 风险：这些状态不受 `CombatService.unregisterMob` 统一管理，清理依赖技能内部任务检测和当前未使用的 `onUnequip`；后续增加有状态技能时容易形成新的生命周期孤岛。
- 建议方向：评估将每只怪物的技能运行状态收拢到 `MobState` 或统一的会话管理器，Skill 实现尽量保持无状态。

### 10. 延迟与周期任务缺少统一所有权

- 状态：**待确认**
- 现状：多个技能直接创建延迟或周期任务，例如 `firework`、`ghost`、`morph`、`thief`、`webber`、`mama`、`sulfur`、`spear`、`mounted`。
- 风险：各实现独立决定实体有效性检查、取消条件、配置重载后的参数语义和关服清理，容易出现行为不一致。`ghost` 还使用每 2 tick 自递归调度维持移动。
- 建议方向：逐个审查，不要一次性抽象。优先检查是否持有失效实体、是否有明确终止条件，以及延迟执行前是否重新验证目标和世界状态。
- 处理记录：2026-10-01 先处理 `DualMorphSkill` 和 `PassiveSulfurSkill`。`morph` 任务在 `onUnequip` 时取消；`sulfur` 初始触发后改为脱手任务，使用释放时快照，不再依赖后续实体状态。本条其余技能仍待逐项审查。

## P2：结构与维护性

### 11. `CombatService` 职责过多

- 状态：**已确认（结构问题）**
- 当前职责包括：怪物注册表、拾取物追踪、基础属性、伤害改写、技能分类调度、范围扫描、投射物/烟花/闪电伤害桥接、清理任务、管理指令支持等。
- 影响：任何战斗调整都可能触碰共享大类，难以局部验证；特殊技能逻辑不断向服务内增加分支。
- 建议方向：优先按稳定职责拆分，而不是按传统分层机械拆类。候选边界包括运行时注册表、触发调度、特殊伤害来源和清理生命周期。

- 状态：**已确认（维护性问题）**

- 建议方向：只在处理对应功能时逐步提取数据快照和专用解析器，避免一次性重写全部配置系统。
- 处理记录：2026-09-27 已从 `ConfigLoader` 提取核心不可变模型与 `ConfigParser`，并移除其旧格式兼容、预设解析和名称文件读取职责；`LootConfig` 与命令类其余职责留待对应阶段。

### 13. 配置错误处理存在大量静默忽略
